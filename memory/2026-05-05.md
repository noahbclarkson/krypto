## Critical Finding #1: T68 Hedge Is UNVALIDATED in Live-Compatible Harness

bot.rs currently has:
```rust
// When BTC 21d ATR > 55th pct of 252-bar history → reduce size 45%
let pct_idx = (0.55 * hist.len() as f64) as usize;
if let Some(&pct_55) = hist.get(pct_idx) {
    if atr_21 > pct_55 { size *= 0.45; }
```

But `live_compatible_wf.rs` (the validated harness) has **NO USDT hedge overlay whatsoever**. The harness that produced 87.3% pass / Sharpe 6.638 / 103.8x equity does not include the hedge that bot.rs runs.

The hedge overlay was independently tested in `hedge_overlay_extensive_sweep.rs`. LB=252 data shows pct=0.55 (Sharpe 5.547) vs pct=0.75 (5.513) — marginal +0.034 difference, likely noise. But this comparison tested the hedge ON TOP of ATR_RANK=24, not ATR_RANK=5.

**Bottom line: We are running a different strategy in the live bot than what we validated in the harness. The live bot has additional risk overlays that the walk-forward harness doesn't test. This is a structural trust gap.**

The pct_summary.csv is also numerically broken (Sharpe = -10^15 across all configs) because aggregating across LB=504 introduces catastrophic values. The "pct=0.55 beats pct=0.75" finding is only valid within LB=252, and even there the delta is noise-level (+0.034 Sharpe).

## Critical Finding #2: ATR_RANK=5 Is Our Biggest Existential Risk

**ATR_RANK=5 costs ~70% of equity** (112x → ~33.9x in dual-exit harness).
We have ZERO forward-looking validation on this filter.

The filter blocks entries when BTC 21-bar ATR is below the 5th percentile of its 252-bar history. The hypothesis: low-vol chop regimes are whipsaw traps, skip them. This is plausible but **completely unvalidated in forward time**.

Current market regime (2026): BTC has been choppy/bear. If ATR_RANK=5 fires frequently in chop (which it would), the live bot would be sitting in cash while the backtested equity (which includes those periods with ATR_RANK=5 filtering) shows 112x. But if the filter is too aggressive, we'd miss the exact recoveries that the backtest captures.

**We do not know if ATR_RANK=5 is helping or hurting in the current regime.** This is the most important unanswered question in the project.

## Critical Finding #4: T63 Has a Mysterious Compilation Bug

turtle_pnl_attribution.rs (the T63 example) and t63_trade_attribution.rs (an alternative) both fail to compile with 23 and 0 errors respectively.

The error "prefix `csv` is unknown" points to rustc mis-parsing the macro expansion of `println!`/`writeln!` chains — the compiler loses track of string boundaries and produces cascading "unknown prefix" errors starting from line ~403. The bytes are clean (pure ASCII), no unusual characters. rustc 1.95.0 appears to hit a parsing edge case with the particular macro pattern in these files.

Two files with identical symptom. Must be something in common between them — likely the writeln! chain pattern. **This needs dedicated debugging (not just "try rebuilding").**
