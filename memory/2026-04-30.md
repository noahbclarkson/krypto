## 2. Critical Bug Found: Fee Accounting Cancels Out in Walkforward

**Location:** `examples/turtle_chandelier_walkforward.rs` lines 184 and 212.

```rust
let entry = entry_px * (1.0 - TAKER_FEE);  // line 184 — WRONG
let exit  = exit_px * (1.0 - TAKER_FEE);    // line 212 — WRONG
```

**Entry fee is charged as `(1 - fee)` — you get MORE shares for your cash (fee is a credit). Exit fee is `(1 - fee)` — you receive LESS proceeds (correct direction, but magnitude is also wrong for a BUY).

**The `(1-fee)` applied to entry is a multiplication that REDUCES cost basis, while `(1-fee)` on exit REDUCES proceeds. These cancel in the return ratio:**

```
exit/entry = [P * (1-fee)] / [P * (1-fee)] = P/P = cancel fees entirely
```

**Result: The walkforward harness runs ZERO-fee simulation.** The fee accounting audit (commit `a1852c18`) tested sensitivity on the WRONG baseline — it confirmed fee degradation on a system that was already fee-free. All walkforward Sharpe numbers (3.147/40-54) are **inflated by ~22-33%** from fee effects alone.

**Correct formulation:**
```rust
let entry = entry_px * (1.0 + TAKER_FEE`  // BUY: pay more to acquire shares
let exit  = exit_px  * (1.0 - TAKER_FEE`  // SELL: receive less proceeds
```

**Consequences:**
- True fee-adj walkforward Sharpe is probably **2.2–2.5 range** (not 3.147). Still passes, but the gap to live will be smaller than we project.
- The fee sensitivity audit is NOT a fix — it's measuring the wrong thing.
- The **22-33% fee degradation** cited in MEMORY was computed on a system that already cancelled fees. The real degradation from correct cost modeling would be HIGHER.

**This needs fixing before any live deployment.**
