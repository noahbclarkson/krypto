## Mission: Hyperparameter Optimization — Strip Assumptions

The mission brief asked to audit hardcoded constants, isolate hyperparameters, optimize, and chart.
However, PLAN.md T56 already identified the **single most critical hardcoded error** in the codebase:
`progress_equity_curves.rs` line 875 applies `(1.0 - TAKER_FEE)` to long entries — making entry cheaper, inflating returns.

This is NOT a hyperparameter — it's a **fee accounting bug** that makes every equity figure reported from the progress harness overstated. Fixing it is the highest-leverage assumption-removal possible.

## Step 1: Audit — Confirmed the Bug

```rust
// progress_equity_curves.rs line 875 (WRONG):
let entry = entry_px * (1.0 - TAKER_FEE);

// live_compatible_wf.rs line 198 (CORRECT):
let entry = entry_px * (1.0 + TAKER_FEE);
```

For long positions:
- **Correct:** you pay fee when BUYING → effective entry is higher by the fee
- **Buggy:** `(1 - fee)` makes entry cheaper → the fee "savings" inflate returns

The `(1.0 - TAKER_FEE)` formula would be correct for SHORT positions (sell high, then buy back cheaper).
But this strategy is LONG-only. The bug inflated every long entry's return by ~0.2%.

**Note:** `live_compatible_wf.rs` walk-forward results (55/63 pass, Sharpe 4.91) use CORRECT fee math and are NOT affected.

---

## Step 2: Fix + Rerun

**Fix:** Changed line 875:
```rust
// T56 FIX: long entry pays taker fee (effective entry is higher by fee)
// prior: entry_px * (1.0 - TAKER_FEE) was WRONG — made entry cheaper = inflated returns
// fix: entry_px * (1.0 + TAKER_FEE) + exit_px * (1.0 - TAKER_FEE) for longs
let entry = entry_px * (1.0 + TAKER_FEE);
```

Reran `cargo run --example progress_equity_curves --profile sweep`.

## What This Means for the Project

The HOF "86.9x / Sharpe 0.43" is now the **honest daily equity figure** for Turtle+Chandelier.
The walk-forward Sharpe (4.91 from `live_compatible_wf`, which uses correct fee math) remains the right OOS validation metric.
**Never compare walk-forward Sharpe to daily equity Sharpe** — they measure different things.

**Key lesson:** The `(1 - fee)` pattern appears correct for the net-return formula (`exit/entry - 1`) only when entry and exit fees both use the same `(1 - fee)` pattern. But since you PAY fee on entry (not receive it), `entry*(1+fee)` is correct. The bug cancelled incorrectly, making the strategy look more profitable than it is.
